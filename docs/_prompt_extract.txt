Master Development Prompt (Revised):
Tanzanian Regional Referral Hospital HMS
Phased, security-hardened rewrite with a full hospital-grade UI specification
How to use this prompt
Paste Part A (Context), Part B (Security), Part C (Clinical Safety) and Part D (UI Design
System) at the start of every session, then paste one phase from Part E at a time. Do not
ask for the whole system in one request. After each phase, review the output against that
phase's acceptance criteria before starting the next.
Part A: Context and constraints
Role. You are a senior Laravel architect and healthcare-systems engineer. Build a Hospital
Management System (HMS) for a Tanzanian Regional Referral Hospital.
Pinned stack.
PHP 8.3, Laravel 11 (or current LTS if newer), MySQL 8.0, Redis 7, Nginx + PHP-FPM,
Linux (Ubuntu LTS).
Core is PHP/Laravel and MySQL. The following named supporting services are
permitted and nothing else without justification: Redis (cache, sessions, queues),
Nginx, Orthanc (DICOM/PACS), an HL7/ASTM interface engine or library for analysers,
and a CDN for static assets only.
Front end: server-rendered Blade templates with plain CSS (design tokens in Part D)
and a minimal amount of vanilla JavaScript or Alpine.js. No SPA framework, no external
CDN fonts or scripts at runtime.
Hosting and data residency. Assume an on-premises or in-country server environment
with intermittent power and connectivity. All personal health data must remain in
Tanzania.
Facility model. Multi-facility ready from day one (facility_id on all tenant-scoped tables),
initially deployed for one regional referral hospital.
Languages. Swahili and English, complete coverage, switchable per user. All strings in
language files, none hardcoded.

Tanzania Personal Data Protection Act (2022): consent capture, purpose limitation,

National standards: GoT-HoMIS, DHIS2 (MTUHA aggregates), HL7 FHIR for patient

Part B: Security and privacy requirements (non-negotiable)
Access control
RBAC with granular permissions, plus object-level checks in Laravel Policies: facility,
department and care-relationship (a clinician sees patients assigned to or
encountered by their unit unless break-glass is used).
Break-glass access: requires a reason, time-limited, notifies the privacy officer, and
appears in a review queue.
MFA (TOTP) mandatory for administrators and prescribers; configurable for others.
Session idle timeout 15 minutes (configurable), absolute timeout 12 hours, concurrent-
session policy.
Password policy: minimum length 12, breach-list check, lockout with backoff, forced
reset on first login.

Credentials and keys
Two distinct stores:
1. Outbound secrets (NHIF username/password, MoH X-Service-Token , DHIS2
credentials): encrypted at rest with Laravel encryption (key from environment,
rotatable), editable only by ICT administrators, never displayed after saving, never
written to logs.
2. Inbound API keys issued to other systems: generated once, shown once, stored
hashed only, with scopes, expiry, per-key rate limits, last-used time and usage log.
Redact Authorization , X-Service-Token , passwords and national IDs from all logs
and error reports.
Data protection
HTTPS only with HSTS. Redis requires authentication, binds to a private interface and
uses TLS; treat Redis as a store of patient data.
Page/fragment caching is restricted to genuinely public pages. Never cache patient-
identifiable pages or reports.
Encrypt sensitive columns (national ID, phone, next of kin) at the application layer;
encrypted backups, off-site copy, quarterly restore tests, targets RPO 15 minutes and
RTO 4 hours (configurable).
Application hardening
CSRF protection, output escaping everywhere (clinical free text is untrusted),
parameterised queries only, $fillable  allow-lists (no mass-assignment), strict file-
upload validation (type, size, content sniffing, storage outside web root, malware scan
hook).
Security headers (CSP without inline scripts, X-Frame-Options, Referrer-Policy,
Permissions-Policy).
Dependency scanning in CI (composer audit), static analysis (Larastan level 8), and a
documented penetration-test checklist to complete before go-live.
Audit
Append-only audit log covering reads and writes of patient records, logins, permission
changes, key operations, exports, prints and break-glass use. Record user, role, facility,
patient, action, timestamp, IP and device.
Clinical records are versioned and never hard-deleted. Corrections create a new
version with a reason; cancelled items are voided with a reason.

Part C: Clinical safety requirements
Read-your-writes consistency: clinical reads (allergies, active medications, orders,
results) must go to the primary database or verify replica lag below a set threshold.
Replicas may serve reports and non-critical lists only.
Cache invalidation: drug formulary, tariffs and rosters are cached in Redis with explicit
invalidation on change and a maximum TTL. Allergy, medication and result data are
never served from a stale cache.
Decision support is deterministic and rule-based: drug-drug interaction, allergy
conflict, duplicate therapy, renal/paediatric/pregnancy dose-range and maximum-dose
checks. Name the source dataset in configuration (for example a licensed interaction
database or the Tanzania Standard Treatment Guidelines and National Essential
Medicines List). Every alert shows its rule, severity and source; overrides require a
coded reason and are audited.
Patient identity: unique MRN generated concurrency-safely (database sequence or
locked counter), master patient index with probabilistic duplicate detection, merge
and unmerge workflows with full audit, optional NIDA verification.
Positive patient identification: two-identifier confirmation and barcode scanning at
specimen collection, dispensing and medication administration.
Claims safety: NHIF claim submission uses idempotency keys, a retry policy with
backoff, a dead-letter queue, and visible rejection handling with reason codes. A claim
can never be submitted twice for the same folio.
Downtime operation: local-first read access to a downtime summary (current
inpatients, allergies, active medications), printable downtime forms, and a paper-to-
system reconciliation screen that records who back-entered what and when.

Part D: UI design system (hospital-grade, no decoration, no AI
features)
D1. Design principles
1. Clinical clarity over appearance. The interface exists to prevent errors and save time
at the point of care.
2. Plain, neutral, predictable. The same pattern for the same task everywhere.
3. Information density with legibility. Clinicians need to see more, not less, without
squinting.
4. Safety-critical information is never hidden (allergies, alerts, patient identity, location).
5. Works on poor infrastructure: low bandwidth, older browsers, shared workstations,
intermittent power.
D2. Strict prohibitions
The following must not appear anywhere: UI, notifications, emails, SMS templates, PDFs,
seed data, error messages, documentation or code comments.
No emoji or emoticons of any kind, and no decorative Unicode symbols used as icons.
No AI-like features or styling: no chatbot or assistant panel, no "Ask AI" or "Suggest"
buttons, no sparkle or magic-wand icons, no auto-generated summaries or narrative
text, no predictive or "smart" autofill of clinical free text, no generated
recommendations presented as advice, no "insights" widgets.
No conversational or personalised microcopy: no greetings such as "Good morning,
Doctor", no motivational or celebratory messages, no mascots, no first-person system
voice ("I found..."). Use neutral, imperative, factual text.
No decorative effects: no gradients, glassmorphism, glow, parallax, animated
illustrations, confetti, skeleton shimmer, or auto-playing motion. Transitions limited to
instant state changes; honour prefers-reduced-motion .
No stock imagery, illustration or marketing-style hero sections. Login page shows
facility name, logo, and the form.
Rule-based clinical alerts are permitted and are presented as plain alerts (see D8),
never described as intelligent or AI.
D3. Visual foundation (design tokens)
Define as CSS custom properties; light theme only (a high-contrast variant is optional).

D5. Core components
Data tables: sticky header, server-side sorting, filtering and pagination, column
chooser, keyboard row navigation, selected-row highlight, row actions as text links or
buttons, CSV and PDF export where permitted. Empty states show a plain sentence
and the available action.
Forms: labels above fields, never placeholder-as-label; required fields marked with the
word "Required"; units shown beside numeric inputs; inline validation on blur with
specific messages; logical tab order; autosave of drafts for long clinical notes with a
visible "Draft saved at HH:MM" indicator. Dates as dd/mm/yyyy, time as 24-hour,
timezone Africa/Dar_es_Salaam.
Buttons: one primary action per view (filled --primary ), secondary actions outlined,
destructive actions use --critical  and always require confirmation. Button text
states the action ("Save encounter", "Dispense", "Submit claim").
Dialogs: used only for confirmation and short inputs. Critical confirmations restate the
patient name and MRN and the exact action.
Alerts and banners: four types (Critical, Warning, Info, Success), each with a text label,
short message and, where relevant, the rule or reference. Critical alerts require
acknowledgement and are logged.
Status tags: square-cornered text tags ("Pending", "In progress", "Verified",
"Cancelled"), consistent vocabulary across modules.
Charts: only where they serve clinical work (vital signs trends, growth charts,
partograph, epidemic curve), drawn with accessible, labelled axes, data table
alternative available. No decorative KPI tiles.
